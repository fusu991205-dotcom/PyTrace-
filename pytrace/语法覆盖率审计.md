# 语法 / 语义覆盖率审计（诚实版）

> 审计方式：**以真实 Python 输出为基准，逐类对比各通道的输出**
> 审计脚本：`tests/执行式覆盖率审计.py`（三通道对比）、`tests/构造覆盖率审计.py`（历史基线）
>
> **阅读顺序**：第一节~第二节是**整改前的基线**（推演通道 17%），第七节是**本轮已落地的整改结果**
> （执行式通道 81/81 = 100%）。保留基线是为了说清"为什么必须换架构"。

## 一、结论先行

| 指标 | 结果 |
|---|---|
| 58 个原生语法用例，输出与真实 Python **完全一致** | **10 个（17%）** |
| 完全不支持的类别 | 容器/推导式、字符串格式化、异常处理、对象/类、装饰器、生成器/异步、标准库、字符串方法链 |

**这不是"漏了几个特例"，是架构层面的先天限制**：当前「逻辑推演」是自己用 AST 重写了一遍 Python 语义
（`_Simulator._ev` 只认字面量、四则运算和少数内置函数），而真实 Python 语义极其庞大
（对象协议、魔术方法、描述符、推导式作用域、生成器状态机、异常链、装饰器包装……）。
重写到什么程度都不算完，且每加一条都是"特例补丁"。

## 二、实测明细（58 用例）

| 类别 | 通过率 | 典型失败（真实 → 推演） |
|---|---|---|
| 表达式 / 运算符 | 5/9（55%） | `1<2<3 → True` vs `1 < 2 < 3`；海象 `(n:=5)` 失效；解包 `a,*b=[1,2,3]` 失效 |
| 字符串格式化 | 0/2（0%） | `f"{x:>8.2f}" → 3.14` vs `3.14159`（格式说明符被忽略） |
| 容器 / 推导式 | 0/9（0%） | `[i*2 for i in range(4)] → [0,4]` vs 原样符号；`l.append/sort/pop`、`d.get/setdefault`、`del`、集合运算全失效 |
| 内置函数 / 类型 | 1/5（20%） | `max/abs/round/any/all/list/tuple/set/isinstance/type` 未实现 |
| 控制流 | 2/7（28%） | `for-else`/`while-else` 的 else 分支不执行；`match/case` 完全没实现 |
| 异常处理 | 0/4（0%） | `try/except/else/finally` 只走 try 体；`raise ... from` 丢链；多种 except 一律走最后一个 |
| 对象 / 类 | 0/5（0%） | 继承 + `super()` 不解析；`property/classmethod/staticmethod` 无描述符语义；`__add__/__repr__` 魔术方法不生效；`dataclass`、`with` 协议缺失 |
| 函数 / 作用域 | 2/9（22%） | `*args/**kwargs` 打包错误、`nonlocal`/`global` 不生效、返回值解包 `x,y=f()` 失效 |
| 生成器 / 异步 | 0/2（0%） | `yield`/`yield from` 状态机缺失；`async/await` 只当普通函数 |
| 装饰器 | 0/4（0%） | 自定义装饰器、带参装饰器、多重装饰器、类装饰器**一律不执行包装逻辑**（只是打了说明文字） |
| 标准库 | 0/1（0%） | `math.pi`、`math.sqrt` 不解析（import 只是"登记"） |
| 字符串方法链 | 0/1（0%） | `.strip().split(",")[0].upper()` 全链失效 |

> 注：上一轮做的「框架回调演示」是**壳对了、里子没对**——`logger`/`try` 走了一遍，但
> `request.tool_call['name']` 这类取值全是符号，无法给出真实值。

## 三、GitHub 成熟项目怎么做的（关键对比）

| 项目 | 采集方式 | 支撑的语义范围 | 依赖要求 |
|---|---|---|---|
| **Python Tutor**（pg_logger.py） | **真实执行**：bdb/settrace 逐行记录所有数据结构，前端前进/后退播放 | 完整 CPython 语义（含类、继承、生成器、异常）；不支持第三方库 | 服务端执行，自带 fake module 机制 |
| **VizTracer** | **真实执行**：sys.setprofile/sys.monitoring，采函数进出+入参 | 完整语义；额外支持多线程/多进程/async/PyTorch | 需要装得上依赖 |
| **Birdseye** | **运行时 AST 插桩**，记录每个子表达式的真实值 | 完整语义（表达式级） | 需真实运行 |
| **snoop / PySnooper** | 装饰器 + 真实 trace，打印逐行变量 | 完整语义 | 需真实运行 |
| **heartrate** | 真实 trace + 实时行命中可视化 | 完整语义 | 需真实运行 |
| **PyTrace（当前）** | **AST 静态模拟**（自己重写语义） | ≈17% 原生语法 | 零依赖 |

**共同点：无一例外都是"真实解释执行 + 观测"，没有人重写语义。** 这正是我们 17% 的根因。
我们为了"不依赖对方环境装包"而放弃了真实执行——但这两件事**可以解耦**：
真实执行 + 把缺失的第三方包替换成桩对象，就能既零依赖、又拿到真实语义。

## 四、改进方案：三通道架构

```
                    ┌─ 通道 A 执行式推演（新，主通道）───────────────┐
用户代码 ──► 判定 ──┤ 真实解释执行 + settrace 探针 + 缺失依赖桩化    │──► 真实值事件流
                    │ 命中率≈原生语义 100%（std 库+用户代码）      │    + AST 语义卡片合并
                    ├─ 通道 B 语义卡片（保留）──────────────────────┤
                    │ 只出人话解释，不做求值（解释层与求值层解耦）  │
                    ├─ 通道 C AST 推演（兜底）──────────────────────┤
                    └─ 代码无法执行（语法级/极端副作用）时降级 ─────┘
```

### 通道 A：执行式推演（核心）

1. **复用现有 `runner.py`**：`sys.settrace` 已经是真实执行探针，入参/出参/异常/stdout 都已采集，
   只是遇到 `ModuleNotFoundError` 就断了
2. **缺失依赖桩化**（已在 `tests/依赖桩原型.py` 验证通过）：
   - `sys.meta_path` 注入 Finder：`import langchain` 找不到 → 生成桩模块，**不报错**
   - 桩对象支持：调用、属性链、下标、类型注解 `A | B`、`bool/str` —— 实测 `agent_tools.py` 已能跑通完整模块级代码
   - 真实依赖存在时（用户自己的环境）走真实包，签名/文档更准
3. **AST 语义卡片叠加**：执行事件流里每条 line 事件按行号挂上 `explain`（复用现有 `_stmt_semantics`），
   于是"真实值 + 人话解释"同时具备，解释层不再依赖模拟器
4. **副作用护栏**（必须同步做，否则危险）：
   - `socket` 连接、`requests` 等网络调用 → 拦截并返回桩（或显式报"已拦截"）
   - 文件写入/删除 → 只读模式（`open(mode='w')` 拦截并提示）
   - 超时（默认 10s）、事件上限（现 8 万）、递归深度上限
   - 演示版（`PYTRACE_DEMO=1`）继续走白名单，不允许任意代码执行
5. **降级链路**：执行失败（SyntaxError → 已有；超时/崩溃/被护栏拦死）→ 自动回退通道 C，
   并在界面明确标注「当前为结构推演，值不确定」

### 通道 B：语义卡片（保留，价值不冲突）

现有装饰器/入口/类/链式调用/import 的 explain 文案全部保留，只是**从"求值者"变成"注解者"**：
- 执行模式下：真实事件 + 卡片解释（最佳组合）
- 兜底模式下：卡片解释 + 符号值（明确标注不确定）

### 通道 C：AST 推演（兜底，不再当主力）

保留现有 `_Simulator`，定位改为"跑不起来时也能讲结构"。不再往里面堆语义特例
（继续堆是死路，见第 2 节数据）。

## 五、分阶段实施

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0（本轮，1 次迭代）** | 通道 A 骨架：桩化 import + 执行式推演端点 + 语义卡片合并 + 护栏（网络/文件写/超时）+ 前端模式标识 | 58 用例通过率 ≥ 85%（预计 ≥ 95%）；`agent_tools.py`/`middleware.py`/`rag.py` 全部可执行 |
| **P1** | 桩对象升维：`__or__`/迭代/索引/算术/上下文管理器；框架回调"驱动演示"（给定钩子函数自动构造入参调用一次） | 中间件类文件也能看到函数体真实执行 |
| **P2** | 交互增强：表达式级子值（借鉴 Birdseye）、数据结构图（借鉴 memory_graph）、失败点自动定位 | 新手可定位"哪一步值不对" |

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 执行用户代码有副作用（删文件、发请求） | P0 内置护栏：网络拦截、写文件拦截、超时、事件上限；界面明示"已拦截 N 个副作用调用" |
| 桩对象行为与真实包不一致 | 界面标注"该对象为依赖桩，非真实包"；用户自己环境可用真包（后续插件） |
| 执行比 AST 慢 | 复用 runner 现有事件上限与降采样；实测 rag.py 真实 trace 在秒级 |
| 演示版被滥用 | 演示版保持白名单 + 拒绝任意上传执行 |

## 七、已落地的整改（本轮）

审计结论直接推动了架构调整，三通道方案里的**通道 A 已经做完并实测通过**，不再是纸面计划。

| 整改项 | 落地位置 | 实测结果 |
|---|---|---|
| 执行式成为主通道 | `/ws/run` + `runner.py`（原有探针）+ 前端「运行」按钮 | 81 个原生语法用例 **81/81 = 100%**，与真实 `python3` 输出逐字一致 |
| 缺失依赖自动桩化 | 新增 `guard.py`：`Stub` / `StubModule` + `runner.py` 的 import 钩子 | `agent_tools.py`、`middleware.py`、`rag.py` 在缺 langchain/langgraph/utils 的环境下也能执行到模块级代码 |
| 装饰器透明化 | `Stub.__call__`：被当装饰器且参数是函数时**返回原函数** | `@tool` / `@tool(description=...)` 未安装时，函数体仍真实执行（`search("abc") → 结果:ABC`） |
| 副作用护栏 | `guard.py::install_guard` | 拦截联网、越界写盘、子进程；`sleep` 压缩到 0.3s；每类拦截发一条 note |
| 语义卡片叠加 | `app.py::_line_annotations` + `_pump` | 真实执行的行事件带 `explain`，逐行说明覆盖 91%~100% |
| 逐行说明扩容 | `_stmt_semantics` 补齐 assign / call / return / for / while / if / try / raise / assert / with / del | 从 12% 提升到 91%+ |

## 八、还剩什么没做（诚实清单）

| 项 | 现状 | 说明 |
|---|---|---|
| 桩对象与真实库的行为差异 | 可继续执行，但值不可信 | 界面已标「未安装·占位」；想让值真实，需要在用户自己机器上跑（本地版天然满足） |
| 框架回调的真实驱动 | 仅"保留函数体" | `@wrap_tool_call` 这类回调不会自动被调用一次；P1 计划做"给定钩子自动构造入参调用一次" |
| 表达式级子值（`a.b[0]+c` 每一步） | 未做 | 借鉴 Birdseye 的 AST 插桩，P2 |
| 数据结构图 | 未做 | 借鉴 memory_graph，P2 |
| 多进程/子解释器 | 未采集 | VizTracer 有，我们只跟主进程 |
| 性能（百万行循环） | 降采样 | 已有 LINE_BUDGET 与事件上限 |
